# R15 display geometry audit (read-only source investigation)

The R15 capture and active HakiOS sources disagree about the display profile. The real output is BGR24, 1080 x 2040, with 3240 bytes per row. The UI render surface is BGRA32, 750 x 1334, with its own aligned stride of 3072 bytes. These are separate buffers and their different strides are intentional. There is no observed 810-pixel-wide buffer: 3240 / 3 = 1080, whereas dividing this BGR24 row by 4 applies the wrong pixel format.

The source and log are consistent about storage formats and physical width. The concrete inconsistency is 750 x 1334 being presented with scale 3 and artwork subtype 2436. The calculated narrow logical width is a strong explanation for large icons, cropped Dock content and overlapping labels, but the final causal claim needs actual MobileGestalt/UIKit measurements and a photograph after correction.

## Minimal proposed revision

1. Preserve every R15 payload boot-argument byte, including bootcpu=1 cpus=1, fbwidth=750 fbheight=1334 and the timer. Preserve CPU, UFS, RAM, journal and flush settings.
2. For Lithium's exact 750 x 1334 configuration with no explicit fbscale/fbsubtype override, use the existing upstream profile mechanism with scale 2 and artwork subtype 1334. This yields a coherent intended 375 x 667 logical canvas. Other geometries and explicit overrides retain upstream behavior.
3. Leave BGR24 scanout and both buffer strides intact. Leave the compositor's full-panel mapping intact in this revision: it already maps the complete source into panel bounds, and changing its geometry would confound the UI-profile correction. The small aspect-ratio stretch remains a known limitation.
4. Avoid installing the iPhone X split status-bar fallback when the actual device tree has the coherent 2x/1334 profile; let UIKit choose its native provider.
5. Log device-tree values before/after the change, physical/render sizes and format/stride. From SpringBoard's main queue, log real MobileGestalt ScreenDimensions and related keys, UIScreen bounds/nativeBounds/scale/nativeScale, and bounded window frames.
6. Build and freeze a new revision after source backup and validation. No userdata rewrite and no phone restart during preparation.
